# Script JVM bytecode target

Status: Retain JVM target 1.8 for M8; accepted on 2026-08-25

## Current contract

The embedded Kotlin compiler is explicitly invoked with `jvmTarget = "1.8"`. The entry analyzer
accepts class-file major versions 45 through 52 and rejects anything newer before JAR publication or
D8. The compiler option is included in the compilation-cache identity, while the compiler and D8
versions also participate in the advertised toolchain fingerprint and canonical cache key.

The APK has minSdk 26, but the frozen Protocol 1.1 request profile and D8 invocation use min API 24.
Those Android API numbers are separate from the JVM class-file target. Kotlin's official compiler
reference describes `-jvm-target` as the generated bytecode version and still lists `1.8` as the
default. Android's Java-version guidance likewise distinguishes build JDK, source features, class
format, Android platform APIs, and desugared library APIs:

- [Kotlin/JVM compiler options](https://kotlinlang.org/docs/compiler-reference.html#jvm-target-version)
- [Java versions in Android builds](https://developer.android.com/build/jdks)
- [D8 bytecode-to-DEX tool](https://developer.android.com/tools/d8)
- [Java 8+ API desugaring](https://developer.android.com/studio/write/java8-support)

Core-library desugaring can supply selected newer Java library APIs; it does not by itself broaden
the provider's controlled script compile classpath (`API 24 class stubs + entry API + stdlib`) or
make a higher class-file version part of this provider's validated contract.

## Evaluation of 11 and 17

Higher targets can let the compiler use newer JVM representations and may improve particular code
shapes. For this single-file Android pipeline, the immediate benefit is small: scripts are converted
to DEX before execution, receive no general JDK, and already get Kotlin language features that lower
to Java 8 bytecode.

Changing the string alone is unsafe:

1. JVM 11 and 17 output uses class-file major 55 and 61, respectively; the current entry analyzer
   deliberately rejects both. `EntryClassAnalyzerTest.classFilesAboveJava8RemainOutsideTheValidatedRuntimeContract`
   pins this fail-closed boundary.
2. Every generated class shape—including nested, default-interface, lambda, and debug metadata—must
   survive the provider's exact analyzer → deterministic JAR → D8 8.13.17 → strict single-DEX path.
3. The minimum-device matrix must distinguish language desugaring from library API availability.
   Android's official table notes Java 11 platform support around Android 12/13 and Java 17 core
   libraries at Android 14; this plugin must continue to work from its declared Android 8.0 floor.
4. A target change invalidates compilation cache identity and release evidence even if source and
   compiler version remain unchanged.

## Decision

Keep `KotlinJvmCompiler.JVM_TARGET = "1.8"` and class major 52 as the maximum for `0.5.0-m8`.
Do not couple a runtime bytecode-contract change to the source-diagnostic milestone.

An upgrade to 11 or 17 requires one dedicated candidate branch and all of these gates:

1. parameterize the analyzer's admitted class version and add real Kotlin target-11/17 fixtures;
2. compile each fixture with the embedded compiler, rebuild the validated JAR, run the pinned D8,
   validate the resulting DEX descriptors/version, and execute it in a disposable worker;
3. cover default methods, lambdas, nested classes, `invokedynamic`-eligible string concatenation,
   source line tables, and a deliberately unavailable Java library API;
4. run the complete unit/Lint/archive gates plus device execution on API 26 and the designated API
   31 device, with no increase to the declared minimum SDK;
5. update cache-option identity, toolchain/release records, compatibility documentation, and APK
   size/latency baselines in the same release.

If those gates show no material script or performance benefit, remain on 1.8. A newer Gradle build
JDK is not, by itself, a reason to change the bytecode emitted for untrusted scripts.
