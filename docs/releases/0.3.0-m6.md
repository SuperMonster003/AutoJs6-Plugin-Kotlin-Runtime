### Production host/provider path

`samples/m5-capabilities.kt` ran through AutoJs6 and exercised all four Protocol 1.1 capabilities:

- `APP_LAUNCH`: returned `true` and brought AutoJs6 to the foreground.
- `CONSOLE_STREAM`: emitted the expected start, stdout, stderr, and terminal markers.
- `SLEEP`: completed the 500 ms cancellable sleep.
- `TOAST`: the expected toast was observed.

The first end-to-end run completed in 7,107 ms and an immediate second run in 1,157 ms. This is
the production-path warm-cache signal; cache hit/miss authentication and telemetry semantics are
covered directly by unit tests because Protocol 1.1 intentionally exports no cache-specific result
field. After restoring the release APK from the instrumentation target, a capability run completed
successfully in 2.210 seconds. The canonical APK built from the pushed tag was then installed with
`adb install -r`; the same production-path sample completed in 2.211 seconds with app launch,
stdout/stderr, Unicode text, toast, and sleep markers all observed. Its disposable worker exited
after completion while the compiler process remained healthy.

### Active cancellation and worker retirement

While `samples/m6-cancellation.kt` was sleeping, AutoJs6 ran `samples/m6-host-cancel.js`, which
invokes the host's `engines.stopAll()` API. Evidence:

- `M6_CANCELLATION_STARTED` was emitted while a fresh `:worker` process was present.
- `M6_HOST_CANCEL_REQUESTED` was emitted by the host-side cancellation helper.
- AutoJs6 reported `[JVM_SOURCE_CANCELLED] JVM source execution was cancelled`.
- The disposable worker was present at 250 ms and absent by the 500 ms observation; it remained
  absent through 7 seconds, while the separate `:compiler` process stayed healthy.
- `M6_CANCELLATION_UNEXPECTED_COMPLETION` was never emitted.

The device's accessibility-service setting was restored byte-for-byte after an earlier volume-key
probe, and the final cancellation path did not require changing that setting.
