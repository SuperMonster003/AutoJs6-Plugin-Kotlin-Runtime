Production changes are intentionally small:

- `app.launch` and `toast.show` use one executable worker-side pipeline in the fixed order
  authorization → payload validation → dispatch → response validation;
- each stage has short-circuit unit tests, so a failed earlier stage cannot reach a host operation;
- schema-2 protocol provenance now requires a clean host commit, `debug` variant, exact source task
  and output, complete row/field sets, and exact committed AAR digest;
- the existing failure-path gate now proves both `sourceDirty=true` and a one-byte AAR mutation are
  rejected;
- provider metadata, capabilities, Entry API, AARs and host-call payloads remain Protocol 1.1.

## Protocol 1.2 proposal boundary

The host proposal covers five candidate families in priority order:

1. bounded plain-text `clipboard.read/write` with foreground and sensitive-content rules;
2. `storage.read/write` through host-owned opaque document grants;
3. `http.request` through an exact-origin HTTPS proxy with redirect and SSRF checks;
4. `notification.post` through a host-owned channel and platform permission;
5. `engines.exec`, explicitly deferred until recursion, child cancellation and delegated privilege
   rules are solved.

Every candidate has a user-grant model, canonical JSON shape, request/response limit, rate limit,
timeout, stable public errors and negative conformance cases. Unknown future capability names are
proposed as optional tagged strings rather than new values in the required Protocol 1.1 enum list,
because the current host reads capabilities before it can send the negotiated version.

No candidate is enabled until matching host policy, Entry API 3, Java and Kotlin providers, frozen
AARs, unit tests and same-signer device conformance land together. The normative proposal draft is
[`docs/proposals/jvm-source-protocol-1.2-capabilities.md`](../proposals/jvm-source-protocol-1.2-capabilities.md).
